\section{Backend REST API con FastAPI}
Per mettere in comunicazione il layer \textbf{Gold} di MongoDB, il motore di \textbf{anomaly detection} e l'interfaccia web, abbiamo sviluppato un backend REST in Python basato sul framework \textbf{FastAPI}, contenuto nel file \texttt{api/main.py} ed eseguito nel container Docker \texttt{vitaldb\_api} sulla porta \texttt{8000}.

Abbiamo scelto FastAPI per tre motivi pratici:
\begin{enumerate}
    \item permette di definire le rotte HTTP in poche righe di codice con validazione automatica dei tipi dei parametri (come \texttt{case\_id: int} e \texttt{window\_seconds: Optional[int]});
    \item genera automaticamente la documentazione interattiva OpenAPI/Swagger all'indirizzo \texttt{http://localhost:8000/docs}, molto comoda per testare le API anche senza passare dal browser della dashboard;
    \item tramite \texttt{StaticFiles} consente di servire direttamente nello stesso processo \texttt{uvicorn} sia le rotte JSON sia le cartelle statiche \texttt{/dashboard} e \texttt{/presentazione}, evitando di dover configurare un terzo container con un web server separato come Nginx.
\end{enumerate}

A livello di gestione delle risorse, il backend mantiene una variabile globale \texttt{\_client: Optional[MongoClient] = None} inizializzata al primo accesso dalla funzione \texttt{get\_db()}. In questo modo tutte le richieste HTTP condividono lo stesso pool di connessioni TCP di PyMongo verso \texttt{vitaldb\_mongo}, senza dover aprire e chiudere un nuovo socket a ogni chiamata. Inoltre, prima di restituire i dati al client, il backend sostituisce sistematicamente i valori \texttt{np.nan} di Pandas con \texttt{None} (che in JSON diventa \texttt{null}), perché il formato JSON standard non ammette il token \texttt{NaN} e i browser bloccherebbero la decodifica della risposta.

Le rotte esposte da \texttt{api/main.py} sono organizzate come segue:
\begin{itemize}
    \item \texttt{GET /health}: esegue un \texttt{ping} su MongoDB e restituisce lo stato del servizio insieme ai conteggi totali dei documenti presenti in \texttt{registry}, \texttt{vital\_signals} e \texttt{anomalies\_detected};
    \item \texttt{GET /cases}: recupera la lista dei casi certificati chiamando \texttt{list\_loaded\_cases(db)} (che filtra solo \texttt{\{"status": "committed"\}}) e vi unisce reparto (\texttt{department}), età (\texttt{age}) e sesso (\texttt{sex}) tramite una singola pipeline di aggregazione \texttt{\$group} con operatore \texttt{\$first} su \texttt{vital\_signals}. Come visto nel Capitolo~3, questo evita il problema delle $N+1$ query riducendo il caricamento dei 500 casi a 2 sole interrogazioni al database;
    \item \texttt{GET /cases/\{case\_id\}/series}: restituisce la serie temporale del paziente richiesto. Se il client non passa il parametro opzionale \texttt{window\_seconds}, l'endpoint chiama \texttt{get\_case\_series(db, case\_id)} e restituisce il tracciato completo a 1 Hz; se invece viene specificata una finestra (ad esempio \texttt{30}, \texttt{60} o \texttt{300} secondi), chiama \texttt{downsample\_case(db, case\_id, window\_seconds)} che delega a MongoDB il calcolo delle medie temporali con \texttt{\$dateTrunc}, riducendo drasticamente il peso del JSON inviato al browser;
    \item \texttt{POST /cases/\{case\_id\}/detect}: avvia l'esecuzione della pipeline ibrida di rilevamento anomalie sul caso richiesto chiamando \texttt{run\_detection\_pipeline(db, [case\_id])}, salva i risultati in \texttt{anomalies\_detected} con il pattern \textit{Insert-Before-Delete} e restituisce al frontend il conteggio per metodo (\texttt{summary\_by\_method}) e l'elenco dettagliato dei secondi anomali. L'implementazione reale dell'endpoint è riportata nel Listato~\ref{lst:api_detect};
    \item \texttt{GET /quality}, \texttt{GET /benchmark} e \texttt{GET /evaluation}: leggono da disco e restituiscono in JSON i tre report generati dalla pipeline (\texttt{data/quality\_report.json}, \texttt{data/benchmark\_report.json} e \texttt{data/ml\_evaluation.json}), permettendo alla dashboard di mostrare i numeri reali dell'ultimo run eseguito.
\end{itemize}

\begin{lstlisting}
@app.post("/cases/{case_id}/detect")
def detect_case(case_id: int):
    """Esegue l'algoritmo multilivello di Anomaly Detection sul caso specificato."""
    db = get_db()
    df = run_detection_pipeline(db, [case_id])

    if df.empty:
        raise HTTPException(status_code=404, detail=f"Nessun dato temporale disponibile per case_id={case_id}")

    # Individua le colonne marcate come anomalia
    flag_cols = [c for c in df.columns if c.endswith("_anomaly")]
    anomalous_rows = df[df[flag_cols].any(axis=1)]

    # Calcola il conteggio dettagliato per ciascuna metodologia di detection
    summary_by_method = {}
    for col in flag_cols:
        method_name = col.replace("_anomaly", "")
        summary_by_method[method_name] = int(df[col].sum())

    anomalies = []
    for _, row in anomalous_rows.iterrows():
        methods = [c.replace("_anomaly", "") for c in flag_cols if bool(row[c])]
        
        # Converte i valori Float di Pandas sanitizzando eventuali NaN
        hr_val = float(row["Solar8000_HR"]) if "Solar8000_HR" in row and pd.notna(row["Solar8000_HR"]) else None
        spo2_val = float(row["Solar8000_PLETH_SPO2"]) if "Solar8000_PLETH_SPO2" in row and pd.notna(row["Solar8000_PLETH_SPO2"]) else None
        sbp_val = float(row["Solar8000_NIBP_SBP"]) if "Solar8000_NIBP_SBP" in row and pd.notna(row["Solar8000_NIBP_SBP"]) else None
        dbp_val = float(row["Solar8000_NIBP_DBP"]) if "Solar8000_NIBP_DBP" in row and pd.notna(row["Solar8000_NIBP_DBP"]) else None
        mbp_val = float(row["Solar8000_NIBP_MBP"]) if "Solar8000_NIBP_MBP" in row and pd.notna(row["Solar8000_NIBP_MBP"]) else None
        si_val = float(row["shock_index"]) if "shock_index" in row and pd.notna(row["shock_index"]) else None

        anomalies.append({
            "timestamp": str(row["timestamp"]),
            "methods": methods,
            "hr": hr_val, "spo2": spo2_val,
            "sbp": sbp_val, "dbp": dbp_val, "mbp": mbp_val,
            "shock_index": round(si_val, 3) if si_val is not None else None
        })

    return {
        "case_id": case_id,
        "anomaly_count": len(anomalies),
        "summary_by_method": summary_by_method,
        "anomalies": anomalies,
    }
\end{lstlisting}

\begin{techbox}{Limiti del backend REST API}
Nell'implementazione di \texttt{api/main.py} abbiamo individuato alcuni limiti che è opportuno segnalare:
\begin{enumerate}
    \item \textbf{Ricalcolo single-case su \texttt{POST /cases/\{case\_id\}/detect} e assenza di un endpoint \texttt{GET} di sola lettura:} non abbiamo previsto una rotta \texttt{GET /cases/\{case\_id\}/anomalies} che si limiti a leggere da \texttt{anomalies\_detected} i risultati già calcolati dal batch sui 500 casi. Quando l'utente avvia il rilevamento dalla dashboard, l'endpoint \texttt{POST} riesegue \texttt{run\_detection\_pipeline(db, [case\_id])}, riaddestrando Isolation Forest e LSTM Autoencoder sul solo paziente selezionato e sovrascrivendo nel database le anomalie batch di quel caso;
    \item \textbf{Assenza di modelli \texttt{response\_model} Pydantic:} le rotte restituiscono direttamente dizionari Python sanitizzati; di conseguenza la pagina \texttt{/docs} mostra gli endpoint e i parametri di input, ma non espone lo schema tipizzato dei campi di risposta;
    \item \textbf{Dettagli minori di configurazione:} l'istanza \texttt{FastAPI} dichiara \texttt{version="1.0.0"} (mentre \texttt{config.PIPELINE\_VERSION} è \texttt{"1.1.0"}), l'endpoint \texttt{GET /health} conta i documenti di \texttt{registry} con \texttt{count\_documents(\{\})} senza filtrare \texttt{\{"status": "committed"\}}, la rotta radice \texttt{/} restituisce \texttt{404} (poiché la dashboard è montata su \texttt{/dashboard}) e il middleware CORS è lasciato aperto con \texttt{allow\_origins=["*"]} per semplificare lo sviluppo locale.
\end{enumerate}
\end{techbox}

\section{Dashboard web e interfaccia utente interattiva}
Per visualizzare i tracciati dei pazienti, le anomalie rilevate e le metriche dei tre layer abbiamo realizzato una dashboard web moderna accessibile all'indirizzo \texttt{http://localhost:8000/dashboard}.

\paragraph{Scelta tecnologica e architettura modulare del frontend.}
Dal punto di vista tecnologico abbiamo scelto di costruire il frontend in \textbf{HTML5, CSS3 e JavaScript puro (Vanilla JS)}, usando la libreria \textbf{Chart.js} per i grafici, senza introdurre framework come React, Vue o Angular e senza bundler come Webpack o Vite. La motivazione di questa scelta è molto concreta: per una dashboard con due sole viste principali, un framework SPA avrebbe richiesto una catena di compilazione Node.js (\texttt{npm build}) dentro Docker, appesantendo il progetto per ottenere funzioni che potevamo gestire in modo molto più diretto con JavaScript standard.

Per non scrivere comunque tutto l'HTML in un unico file gigante difficile da mantenere, abbiamo creato un piccolo caricatore modulare in \texttt{dashboard/js/loader.js}. Il file principale \texttt{dashboard/index.html} contiene dei tag segnaposto con l'attributo \texttt{data-include} (ad esempio \texttt{<div data-include="partials/sidebar.html"></div>}). All'avvio della pagina, la funzione \texttt{loadPartials()} cerca tutti i nodi \texttt{[data-include]}, scarica in parallelo i frammenti HTML tramite \texttt{Promise.all} e \texttt{fetch} aggiungendo il parametro di versione \texttt{?v=3.9} per evitare problemi di cache del browser (\textit{cache busting}), e infine inizializza gli script della dashboard.

L'interfaccia è divisa in due viste selezionabili dalla barra superiore: la vista clinica (\textit{Clinical Telemetry \& Detection}) e la vista architetturale (\textit{Data Lakehouse \& Benchmarks}).

\section{Containerizzazione Docker, orchestrazione, test (\texttt{pytest}) e reset}
Per rendere il progetto eseguibile allo stesso modo su qualsiasi macchina (Windows, macOS o Linux) senza dover installare manualmente MongoDB 8.0 o configurare ambienti Python locali, abbiamo incapsulato l'intero sistema in due container gestiti da \texttt{docker-compose.yml}, come rappresentato nella Figura~\ref{fig:app_architecture}.

\begin{figure}[ht]
    \centering
    \resizebox{0.95\textwidth}{!}{\input{app_architecture_tikz.tex}}
    \caption{Architettura multi-livello dell'applicazione e containerizzazione Docker Compose.}
    \label{fig:app_architecture}
\end{figure}

I due servizi collegati sulla rete virtuale \texttt{vitaldb\_net} sono:
\begin{enumerate}
    \item \texttt{vitaldb\_mongo} (immagine \texttt{mongo:8.0}): avvia il database con l'opzione \texttt{--replSet rs0}, monta il volume persistente \texttt{mongo\_data} e gli script di inizializzazione in \texttt{/docker-entrypoint-initdb.d/}. Poiché MongoDB richiede alcuni secondi per inizializzare il Replica Set all'avvio, abbiamo configurato un \texttt{healthcheck} basato su \texttt{mongosh} che controlla \texttt{rs.status()} (o lancia \texttt{rs.initiate()} al primo avvio);
    \item \texttt{vitaldb\_api} (costruito dal \texttt{Dockerfile} su base \texttt{python:3.12-slim}): installa le dipendenze di \texttt{requirements.txt} (inclusa la build CPU di PyTorch), monta le cartelle del progetto e avvia \texttt{uvicorn api.main:app --host 0.0.0.0 --port 8000}. Grazie alla clausola \texttt{depends\_on: \{mongo: \{condition: service\_healthy\}\}}, il container dell'API attende che il Replica Set di MongoDB sia effettivamente pronto prima di partire.
\end{enumerate}

\subsection{Orchestrazione della pipeline end-to-end (\texttt{scripts/run\_pipeline.py})}
Nelle prime fasi del progetto, l'avvio della pipeline sui 500 casi richiedeva il lancio manuale in sequenza di 6 comandi separati dentro il container \texttt{vitaldb\_api}:
\begin{enumerate}
    \item \texttt{python src/bronze/download.py --max-cases 500} (genera il nuovo \texttt{run\_id} e scarica il layer Bronze);
    \item \texttt{python src/silver/clean.py} (pulisce i dati, genera il layer Silver e \texttt{data/quality\_report.json});
    \item \texttt{python src/gold/load\_mongo.py} (carica \texttt{vital\_signals} e \texttt{registry} con protocollo a due fasi);
    \item \texttt{python src/detection/detector.py} (esegue regole cliniche + ML e aggiorna \texttt{anomalies\_detected});
    \item \texttt{python src/analysis/benchmark\_etl.py} (aggiorna \texttt{data/benchmark\_report.json});
    \item \texttt{python src/analysis/evaluate\_models.py} (aggiorna \texttt{data/ml\_evaluation.json}).
\end{enumerate}

Un \textbf{limite operativo} che avevamo riscontrato lanciando i singoli comandi da terminale era il rischio di disallineamento dello stato qualora l'esecuzione fosse interrotta prematuramente o eseguita con perimetri eterogenei (ad esempio Bronze scaricato su 500 casi ma Gold rimasto fermo a 50). Per superare questa criticità e garantire riproducibilità deterministica, abbiamo sviluppato lo script orchestratore \texttt{scripts/run\_pipeline.py}, eseguibile direttamente via Docker:
\begin{center}
    \texttt{docker exec vitaldb\_api python -u scripts/run\_pipeline.py}
\end{center}
Lo script incapsula l'intera catena applicando una politica \textbf{fail-fast}: esegue i 6 step in sequenza ordinata, intercetta il codice di uscita di ciascun sottoprocesso e blocca immediatamente l'esecuzione se uno step fallisce (\texttt{exit code != 0}), stampando per ciascuna fase i tempi parziali e la durata complessiva dell'elaborazione.

\subsection{Suite di 38 test automatizzati (\texttt{pytest}) e script di reset}
Per verificare che le modifiche introdotte durante lo sviluppo non rompessero la pulizia dei dati, la governance o le API, abbiamo scritto una suite di \textbf{38 test unitari} eseguibili con \texttt{pytest} e suddivisi nei \textbf{6 moduli reali} presenti nella cartella \texttt{tests/}:
\begin{itemize}
    \item \texttt{tests/test\_config.py} (\textbf{2 test}): verifica che tutte le tracce in \texttt{TRACK\_SPECS} abbiano limiti fisiologici validi ($\min < \max$) e che le costanti cliniche siano coerenti (in particolare che la soglia di freschezza clinica \texttt{NIBP\_MAX\_CLINICAL\_AGE\_S = 120s} non superi mai il limite di \textit{forward-fill} \texttt{NIBP\_STALENESS\_LIMIT\_S = 300s});
    \item \texttt{tests/test\_bronze.py} (\textbf{3 test}): verifica la scrittura atomica su file temporaneo (\texttt{.tmp} $\to$ \texttt{.parquet}), il salvataggio delle tracce del singolo paziente e la generazione di \texttt{download\_manifest.json} con \texttt{run\_id};
    \item \texttt{tests/test\_etl.py} (\textbf{4 test}): collauda le funzioni di \texttt{src/silver/clean.py}, verificando che \texttt{interpolate\_short\_gaps} colmi solo i buchi interni $\le 5\text{ s}$ lasciando \texttt{NaN} le code finali prive di campioni successivi, che \texttt{flag\_outliers} individui gli artefatti prima dell'imputazione, che i 5 flag \texttt{*\_imputed} siano tracciati separatamente per canale e che per ogni traccia valga sempre l'identità $\texttt{observed} + \texttt{imputed} + \texttt{missing} = \texttt{rows\_cleaned}$;
    \item \texttt{tests/test\_gold.py} (\textbf{16 test}): verifica la conversione \texttt{dataframe\_to\_timeseries\_docs} (omissione dei campi \texttt{NaN} e preservazione di \texttt{nibp\_age\_s} e dei 5 flag \texttt{*\_imputed}), il quality gate \texttt{validate\_records}, la struttura del documento \texttt{registry} con \texttt{sensor\_metrics} e \texttt{run\_id}, il filtro \texttt{\{"status": "committed"\}} in \texttt{list\_loaded\_cases} e la funzione di auto-guarigione \texttt{recover\_incomplete\_loads};
    \item \texttt{tests/test\_detection.py} (\textbf{9 test}): verifica il calcolo di Shock Index e ipotensione severa, il silenziamento degli allarmi quando \texttt{nibp\_age\_s > 120s}, l'isolamento delle finestre scorrevoli tra pazienti diversi nell'\texttt{LSTMAutoencoderDetector}, la presenza del proiettore \texttt{nn.Linear} e l'assenza di \textit{data leakage} nel \texttt{.bfill()} raggruppato (\texttt{test\_imputation\_no\_bfill\_leakage\_across\_cases});
    \item \texttt{tests/test\_api.py} (\textbf{4 test}): testa tramite \texttt{TestClient} le rotte \texttt{/health}, \texttt{/cases}, \texttt{/cases/\{id\}/series} e \texttt{POST /cases/\{id\}/detect}. In particolare, in \texttt{test\_api\_detect\_endpoint} abbiamo usato \texttt{monkeypatch.setattr(detector\_mod, "save\_anomalies\_to\_mongo", lambda db, df: len(df))} per evitare che l'esecuzione dei test sovrascrivesse nel database le anomalie reali calcolate sui 500 casi.
\end{itemize}

Infine, per poter ripartire da zero in modo pulito quando necessario, abbiamo predisposto lo script \texttt{scripts/reset\_pipeline.py} (eseguibile con il flag di conferma \texttt{--yes} / \texttt{-y}). Lo script svuota le tre collezioni MongoDB (\texttt{vital\_signals}, \texttt{registry}, \texttt{anomalies\_detected}), cancella i file Parquet dentro \texttt{data/bronze/} e \texttt{data/silver/} e rimuove i 4 file JSON di report insieme a \texttt{data/.current\_run\_id}.

\section{Conclusioni, riepilogo dei limiti per layer e sviluppi futuri}
Il progetto realizzato ci ha permesso di affrontare dall'inizio alla fine tutte le fasi di costruzione di una pipeline dati e di un sistema di \textbf{anomaly detection} su serie storiche cliniche reali, lavorando su una coorte di \textbf{500 interventi chirurgici} del dataset VitalDB (\textbf{5.565.384 righe grezze} in Bronze e \textbf{5.402.386 secondi bonificati} in Silver e Gold).

Dall'esperienza pratica di sviluppo possiamo trarre tre conclusioni principali:
\begin{enumerate}
    \item \textbf{Separare i ruoli dei tre layer (Medallion Architecture) semplifica sia il debug sia le prestazioni:} mantenere il layer \textbf{Bronze} immutabile in Parquet (\textbf{33,95 MB}) ci ha evitato di riscaricare i dati da rete a ogni modifica del codice; usare il layer \textbf{Silver} (\textbf{44,52 MB}, $+31,1\%$) per arricchire i dati con 12 colonne di qualità (\texttt{nibp\_age\_s}, 5 flag \texttt{*\_outlier} e 5 flag \texttt{*\_imputed}) senza cancellare gli outlier ci ha permesso di conservare la tracciabilità completa; infine, delegare al layer \textbf{Gold} su MongoDB 8.0 Time Series il solo dato utile per le query ha ridotto lo spazio fisico dei dati a \textbf{15,60 MB} ($-65,0\%$ rispetto a Silver, più \textbf{2,56 MB} di indici B-Tree) e ha dimezzato il tempo medio di lettura sul singolo paziente (\textbf{12,02 ms} contro \textbf{26,95 ms});
    \item \textbf{La qualità del dato condiziona direttamente gli algoritmi a valle:} scelte apparentemente piccole — come rilevare gli outlier prima del \textit{forward-fill}, limitare la propagazione NIBP a 300 secondi in Silver ma stringerla a $\texttt{nibp\_age\_s} \le 120\text{ s}$ per le regole cliniche, o raggruppare correttamente per \texttt{case\_id} anche il \texttt{.bfill()} — fanno la differenza tra un sistema che genera falsi allarmi continui e uno metodologicamente corretto;
    \item \textbf{Regole cliniche e modelli non supervisionati svolgono compiti diversi ma complementari:} le regole deterministiche danno allarmi immediati e spiegabili su soglie note ($\text{SI} > 0,9$ e $\text{MBP} < 65 \land \text{SpO}_2 < 90\%$), mentre Isolation Forest (PR-AUC $0,105$, $\approx 2,2\times$ il caso) e l'LSTM Autoencoder (PR-AUC $0,067$, $\approx 1,4\times$ il caso) fungono da motori di ranking multivariato sulle 8 feature dinamiche, segnalando anche instabilità del ritmo o cadute rapide sub-soglia.
\end{enumerate}

\subsection{Quadro riepilogativo dei limiti riscontrati lungo l'architettura}
Per offrire una visione d'insieme chiara e onesta del progetto, riassumiamo qui tutti i limiti strutturali e implementativi che abbiamo analizzato nei singoli capitoli, suddivisi per componente:
\begin{itemize}
    \item \textbf{Layer Bronze (\texttt{src/bronze/download.py}):}
    \begin{enumerate}
        \item il controllo di idempotenza sui file già presenti (\texttt{skipped\_existing}) verifica solo il passo tra i primi due campioni (\texttt{Time.iloc[1] - Time.iloc[0]}) e la presenza delle 5 colonne, senza ri-verificare l'integrità dell'intero file;
        \item la tabella \texttt{lab\_data.parquet} viene scaricata con \textit{graceful fallback} ma non viene mai utilizzata nei layer successivi;
        \item il file \texttt{download\_manifest.json} registra il conteggio aggregato dei casi ma non l'elenco o gli hash MD5/SHA256 dei singoli file Parquet.
    \end{enumerate}
    \item \textbf{Layer Silver (\texttt{src/silver/clean.py}):}
    \begin{enumerate}
        \item i valori marcati come \texttt{*\_outlier} non vengono rimossi prima dell'imputazione in Silver: un outlier sul bracciale NIBP può quindi essere propagato in avanti dal \textit{forward-fill} fino a 300 secondi nel file Parquet Silver (problema che abbiamo dovuto neutralizzare a valle mascherando gli outlier a \texttt{NaN} in \texttt{load\_from\_gold});
        \item l'interpolazione lineare ($\le 5\text{ s}$) viene eseguita prima di calcolare la maschera \texttt{was\_na}, perciò i buchi brevi interpolati vengono contati nel report come \texttt{observed} anziché come \texttt{imputed};
        \item non esiste una soglia di scarto per caso (\textit{case-level quality gate}): anche un paziente con lunghi tratti mancanti viene comunque salvato in Silver e passato a Gold.
    \end{enumerate}
    \item \textbf{Layer Gold, Data Lakehouse ``simulato'' e Benchmark (\texttt{src/gold/load\_mongo.py}):}
    \begin{enumerate}
        \item poiché le Time Series Collections di MongoDB 8.0 non supportano \texttt{\$jsonSchema} né transazioni multi-documento verso il \texttt{registry}, le garanzie di schema e di atomicità (\textit{Two-Phase Load}) sono imposte dagli script Python e non dal motore del database;
        \item la lineage del \texttt{run\_id} si ferma al \texttt{registry} e ai file JSON, ma non è scritta dentro i singoli documenti di \texttt{vital\_signals};
        \item il timestamp usa una data base fittizia (\texttt{2020-01-01 + Time}) perché VitalDB fornisce solo i secondi relativi dall'inizio dell'intervento;
        \item nel benchmark (\texttt{benchmark\_etl.py}) il risparmio di storage (\texttt{-54,1\%} vs Bronze, \texttt{-65,0\%} vs Silver) è calcolato su \texttt{gold\_storage\_mb = 15,60 MB} al netto dei \texttt{2,56 MB} di indici B-Tree, e il confronto di latenza legge da Parquet tutte le 18 colonne contro le 14 proiettate da MongoDB.
    \end{enumerate}
    \item \textbf{Anomaly Detection e valutazione ML (\texttt{src/detection/detector.py}, \texttt{evaluate\_models.py}):}
    \begin{enumerate}
        \item fissare \texttt{contamination=0.05} e il $95^\circ$ percentile impone per costruzione che i due modelli ML selezionino sempre circa il 5\% dei punti valutati (agendo come meccanismo di ranking e non come stima della prevalenza reale);
        \item la valutazione si basa su una \textit{pseudo-ground truth} derivata dalle stesse tracce tramite le regole cliniche, misurando quindi la concordanza interna e non la performance su diagnosi mediche indipendenti;
        \item i modelli non vengono salvati su disco (\texttt{.pkl}/\texttt{.pt}) e vengono riaddestrati a ogni esecuzione;
        \item i documenti di \texttt{anomalies\_detected} non contengono un \texttt{detection\_run\_id} che identifichi la versione dei modelli e gli iperparametri usati.
    \end{enumerate}
    \item \textbf{Backend API, Dashboard e Orchestrazione (\texttt{api/main.py}, \texttt{dashboard/}, \texttt{scripts/}):}
    \begin{enumerate}
        \item l'endpoint \texttt{POST /cases/\{id\}/detect} riaddestra i modelli sul singolo paziente selezionato e sovrascrive in \texttt{anomalies\_detected} le anomalie calcolate dal batch sui 500 casi, in assenza di un endpoint \texttt{GET /cases/\{id\}/anomalies} di sola lettura;
        \item la dashboard non visualizza a schermo \texttt{run\_id} e \texttt{pipeline\_version}, mostra solo i primi 15 casi nella tabella Data Quality e mantiene alcuni valori di fallback cablati nel codice client;
        \item l'orchestrazione tramite \texttt{run\_pipeline.py} è sincrona e monoprocesso nel container, priva di un motore distribuito a grafi di dipendenze (DAG) con code asincrone e retry automatici.
    \end{enumerate}
\end{itemize}

\subsection{Sviluppi futuri}
A partire dai limiti appena descritti, le estensioni più naturali per portare il progetto a un livello successivo sono quattro:
\begin{itemize}
    \item \textbf{Salvataggio dei modelli addestrati e separazione tra lettura e ricalcolo nell'API:} serializzare su disco lo \texttt{StandardScaler}, l'istanza di \texttt{IsolationForest} e i pesi PyTorch (\texttt{.pt}) dell'Autoencoder addestrati sui 500 casi, introducendo una rotta \texttt{GET /cases/\{id\}/anomalies} per la consultazione immediata dalla dashboard senza riaddestrare i modelli sul singolo paziente;
    \item \textbf{Doppia lineage granulare (\texttt{pipeline\_run\_id} e \texttt{detection\_run\_id}):} inserire direttamente nei documenti di \texttt{vital\_signals} e \texttt{anomalies\_detected} sia l'identificativo del caricamento dati sia quello dell'esecuzione dei modelli, esponendoli anche nell'intestazione della dashboard;
    \item \textbf{Quality gate bloccante a livello di caso:} introdurre una soglia minima di integrità del dato prima del passaggio a Gold (ad esempio escludere automaticamente dal caricamento i casi con copertura temporale del segnale cardiaco inferiore al $50\%$);
    \item \textbf{Orchestrazione distribuita a DAG e integrazione di nuove tracce VitalDB:} evolvere lo script \texttt{run\_pipeline.py} in un workflow formale con Apache Airflow o Prefect per gestire esecuzioni concorrenti, code di retry ed alert via webhook, ed estendere l'analisi anche alla pressione arteriosa invasiva (\texttt{ART}), alla capnografia ($\text{EtCO}_2$) e all'indice bispettrale (\texttt{BIS}).
\end{itemize}
