\section{Backend REST API con FastAPI}
L'integrazione e la fruizione dei dati archiviati nel livello \textbf{Gold} di MongoDB e l'esecuzione degli algoritmi di rilevamento delle anomalie sono orchestrate da un backend sviluppato in linguaggio Python mediante il framework \textbf{FastAPI}.

La scelta di FastAPI è motivata dalle elevate prestazioni del suo motore asincrono basato su \textbf{Starlette} e \textbf{Pydantic}, che consentono la validazione rigorosa dei parametri di richiesta, la serializzazione nativa dei documenti BSON in formato JSON e la generazione automatica della documentazione interattiva OpenAPI (disponibile all'indirizzo \texttt{/docs}). Il servizio REST opera all'interno del container applicativo \texttt{vitaldb\_api} sulla porta di rete 8000 ed è implementato nel file \texttt{api/main.py}.

Dal punto di vista dell'efficienza delle risorse, il backend gestisce la connettività verso MongoDB mediante un'unica istanza globale del client \texttt{pymongo.MongoClient}. Questo accorgimento implementa un pool di connessioni riutilizzabili (\textbf{connection pooling}) che mantiene aperti i socket TCP tra le varie richieste HTTP, azzerando il costo di negoziazione dell'handshake di rete per ciascuna chiamata all'API. Inoltre, prima della trasmissione dei dati sulla rete, il backend esegue una bonifica dei valori numerici: i valori non validi o mancanti (\texttt{np.nan}) vengono convertiti nel valore Python \texttt{None}, serializzato nel corrispondente valore \texttt{null} standard dello standard JSON. Questa sanitizzazione previene la generazione di token non standard \texttt{NaN}, che provocherebbero errori di decodifica bloccanti nei parser JavaScript dei browser moderni (\texttt{JSON.parse}).

L'interfaccia espone un insieme organico di rotte operative:
l'endpoint \texttt{GET /health}, che svolge la funzione di monitoraggio dello stato di salute del container ed effettua un'interrogazione di ping al database. Esso restituisce un oggetto strutturato contenente lo stato della connettività e le statistiche aggregate di sistema: il numero di casi censiti nel \texttt{registry}, il totale dei punti temporali archiviati in \texttt{vital\_signals} e il conteggio cumulativo delle anomalie salvate in \texttt{anomalies\_detected};
l'endpoint \texttt{GET /cases}, che estrae l'elenco dei casi clinici certificati nel catalogo tramite la funzione \texttt{list\_loaded\_cases(db)}, filtrando rigorosamente i soli record con stato \texttt{\{"status": "committed"\}}. Per prevenire il classico degrado prestazionale dovuto al problema delle $N+1$ query (in cui per ogni caso verrebbe effettuata una lettura distinta per recuperare reparto, età e sesso del paziente), il metodo adotta un'unica pipeline di aggregazione MongoDB con operatori \texttt{\$group} e \texttt{\$first}. Questa ottimizzazione riduce l'intero recupero anagrafico dei 500 pazienti a due sole operazioni complessive sul database;
l'endpoint \texttt{GET /cases/\{case\_id\}/series}, che restituisce la serie temporale biometrica del paziente richiesto. L'endpoint supporta il parametro opzionale \texttt{window\_seconds} (con valori selezionabili quali 30, 60 o 300 secondi): quando specificato, l'API attiva la pipeline di aggregazione temporale descritta nel capitolo precedente con operatore \texttt{\$dateTrunc}, riducendo drasticamente il payload di rete trasferito al browser per tracciati che si estendono per molte ore;
l'endpoint \texttt{POST /cases/\{case\_id\}/detect}, la cui implementazione reale è riportata nel Listato~\ref{lst:api_detect}, innesca l'esecuzione on-demand dell'intera pipeline di \textbf{anomaly detection} sul paziente selezionato invocando \texttt{run\_detection\_pipeline(db, [case\_id])}. La funzione applica automaticamente il mascheramento degli outlier, il filtro di freschezza pressoria ($\texttt{nibp\_age\_s} \le 120\text{ s}$) per le regole cliniche (\textbf{Shock Index} e ipotensione severa), l'inferenza dei modelli \textbf{Isolation Forest} e \textbf{LSTM Autoencoder}, e la persistenza sicura tramite pattern \textit{Insert-Before-Delete} nella collezione \texttt{anomalies\_detected}, restituendo al client sia il riepilogo per metodologia sia il dettaglio sanitizzato degli istanti anomali;
gli endpoint dedicati alla trasparenza e alla governance, segnatamente \texttt{GET /quality}, \texttt{GET /benchmark} e \texttt{GET /evaluation}, che espongono direttamente in formato JSON i report di bonifica del livello \textbf{Silver}, i risultati del benchmark di storage e latenza, e le metriche quantitative di validazione dei modelli di \textbf{machine learning} (tutti corredati da \texttt{run\_id} e \texttt{pipeline\_version}).

\begin{lstlisting}[caption={Definizione della rotta REST per l'esecuzione della pipeline di anomaly detection in FastAPI.}, label={lst:api_detect}]
// Endpoint implementato nel backend FastAPI (api/main.py)
@app.post("/cases/{case_id}/detect")
def detect_case(case_id: int):
    """Esegue l'algoritmo multilivello di Anomaly Detection sul caso specificato."""
    db = get_db()
    # Esegue regole cliniche (con nibp_age_s <= 120s), ML e salvataggio Insert-Before-Delete
    df = run_detection_pipeline(db, [case_id])

    if df.empty:
        raise HTTPException(
            status_code=404,
            detail=f"Nessun dato temporale disponibile per case_id={case_id}"
        )

    flag_cols = [c for c in df.columns if c.endswith("_anomaly")]
    anomalous_rows = df[df[flag_cols].any(axis=1)]

    summary_by_method = {
        col.replace("_anomaly", ""): int(df[col].sum())
        for col in flag_cols
    }

    anomalies = []
    for _, row in anomalous_rows.iterrows():
        methods = [c.replace("_anomaly", "") for c in flag_cols if bool(row[c])]
        hr_val = float(row["Solar8000_HR"]) if pd.notna(row.get("Solar8000_HR")) else None
        spo2_val = float(row["Solar8000_PLETH_SPO2"]) if pd.notna(row.get("Solar8000_PLETH_SPO2")) else None
        sbp_val = float(row["Solar8000_NIBP_SBP"]) if pd.notna(row.get("Solar8000_NIBP_SBP")) else None
        dbp_val = float(row["Solar8000_NIBP_DBP"]) if pd.notna(row.get("Solar8000_NIBP_DBP")) else None
        mbp_val = float(row["Solar8000_NIBP_MBP"]) if pd.notna(row.get("Solar8000_NIBP_MBP")) else None
        si_val = float(row["shock_index"]) if pd.notna(row.get("shock_index")) else None

        anomalies.append({
            "timestamp": str(row["timestamp"]),
            "methods": methods,
            "hr": hr_val, "spo2": spo2_val,
            "sbp": sbp_val, "dbp": dbp_val, "mbp": mbp_val,
            "shock_index": round(si_val, 3) if si_val is not None else None
        })

    return {
        "case_id": case_id,
        "anomaly_count": len(anomalies),
        "summary_by_method": summary_by_method,
        "anomalies": anomalies,
    }
\end{lstlisting}

Accanto agli endpoint analitici, FastAPI ospita due montaggi di file statici: la rotta \texttt{/dashboard}, che distribuisce l'intera interfaccia web interattiva, e la rotta \texttt{/presentazione}, che rende fruibili le slide illustrative del progetto per la discussione accademica.

Come mostrato nella Figura~\ref{fig:dashboard}, l'interfaccia è stata realizzata seguendo i principi di un'estetica moderna e funzionale. Dal punto di vista architetturale, la dashboard rifugge la complessità e la pesantezza di framework monolitici, impiegando standard aperti del web: un'architettura in html5 semantico, fogli di stile css3 con variabili a token per la gestione dinamica del tema chiaro e scuro (\textbf{light/dark mode}), e codice in javascript puro. L'aspetto tipografico è valorizzato da caratteri tipografici dedicati, tra cui \textbf{Figtree} per le intestazioni, \textbf{Space Grotesk} per i testi di interfaccia e \textbf{JetBrains Mono} per i valori numerici e i timestamp.

Per garantire modularità e manutenibilità senza richiedere strumenti di compilazione esterni quali Webpack o Vite, il codice dell'interfaccia adotta un sistema di caricamento modulare asincrono implementato nello script \texttt{dashboard/js/loader.js}. Il file principale \texttt{index.html} definisce dei contenitori dichiarativi denominati slot mediante l'attributo personalizzato \texttt{data-include} (ad esempio \texttt{<div data-include="partials/sidebar.html"></div>}). All'avvio dell'applicazione, la funzione \texttt{loadPartials} individua tutti gli slot mediante \texttt{querySelectorAll}, invia richieste HTTP parallele tramite \texttt{Promise.all} e l'API \texttt{fetch}, e provvede a sostituire ciascun tag con il contenuto HTML recuperato. Al fine di impedire che il browser mantenga in cache versioni obsolete dei file durante gli aggiornamenti, il caricatore accoda a ciascuna richiesta un parametro di versione esplicito (\texttt{?v=3.8}), realizzando una tecnica efficace di invalidazione della cache (\textbf{cache busting}).

La piattaforma si articola su due ambienti di lavoro principali, accessibili tramite selettore in testata: la vista di telemetria clinica e la vista di governance del \textbf{lakehouse}.

\subsection{Vista di telemetria clinica e anomaly detection}
Questo spazio di lavoro è dedicato al monitoraggio del paziente e alla rilevazione delle instabilità. L'ambiente si compone dei seguenti moduli integrati:
la barra laterale (\textbf{sidebar}), che elenca tutti i 500 pazienti certificati nel livello \textbf{Gold} fornendo un campo di ricerca rapida e badge identificativi con reparto chirurgico, età e sesso;
il \textbf{Patient HUD} (Heads-Up Display), un banner informativo collocato in cima alla pagina che visualizza l'identificativo del paziente selezionato, il reparto e i parametri anagrafici. Il modulo ospita i comandi operativi principali: il selettore della risoluzione temporale (che consente di visualizzare il dato grezzo a 1 secondo oppure aggregazioni a 30 secondi, 60 secondi o 5 minuti), il pulsante di ricarica e il pulsante per avviare il calcolo delle anomalie;
la \textbf{Vitals Grid}, una griglia a cinque tessere informative progettata secondo lo stile \textbf{bento-grid}. Ciascuna tessera ospita un indicatore visivo pulsante, il valore medio corrente e il range fisiologico di riferimento per la frequenza cardiaca ($60-100$ bpm), la saturazione d'ossigeno ($95-100\%$), la pressione arteriosa con valore medio ($>65$ mmHg), lo \textbf{Shock Index} e il contatore cumulativo degli eventi anomali rilevati;
la \textbf{Consensus Matrix}, definita nel file \texttt{partials/consensus-matrix.html}, che implementa un pannello interattivo a quattro schede corrispondenti ai quattro metodi di rilevamento (Shock Index, ipotensione severa, Isolation Forest e Autoencoder). Ciascuna scheda mostra un badge con il conteggio in tempo reale degli eventi individuati e consente di cliccare per isolare ed evidenziare sui grafici esclusivamente le anomalie prodotte da quel metodo specifico. Inoltre, ciascuna scheda integra un pulsante informativo che apre una finestra modale con la spiegazione fisiologica, la formula analitica e la soglia di allarme adottata;
i tracciati telemetrici realizzati con la libreria \textbf{Chart.js}: due grafici interattivi sincronizzati ad asse temporale comune. Il grafico superiore traccia l'andamento congiunto di frequenza cardiaca e saturazione, mentre il grafico inferiore visualizza le tre componenti pressorie (sistolica, diastolica e media). I due grafici condividono la traccia di mira (\textbf{crosshair}) e i comandi di ingrandimento temporale, consentendo una correlazione visiva immediata tra alterazioni del ritmo e variazioni pressorie. Quando viene attivato il rilevamento, i punti anomali vengono evidenziati mediante marcatori cromatici sovrapposti alle curve dei segnali;
la tabella analitica delle anomalie, collocata a fondo pagina, che elenca cronologicamente ogni singolo secondo in cui è stata riscontrata un'irregolarità, riportando i valori biometrici istantanei, lo Shock Index calcolato e l'elenco degli algoritmi concordanti.

\subsection{Vista di data lakehouse, governance e benchmark}
La seconda schermata dell'interfaccia, orchestrata dal modulo \texttt{dashboard/js/lakehouse.js} e dal template \texttt{partials/lakehouse-view.html}, visualizza in modo trasparente le metriche di architettura dati e qualità del dato sincronizzate in tempo reale tramite le API REST:
\begin{itemize}
    \item \textbf{Schede comparative di Storage e Query Latency:} illustrano tramite barre grafiche scalate dinamicamente sul massimo ingombro (\texttt{Math.max(bronzeMB, silverMB, goldMB)}) l'evoluzione dello spazio su disco sui 500 casi: dai \textbf{33.95 MB} del livello \textbf{Bronze}, passando per l'espansione del livello \textbf{Silver} a \textbf{44.52 MB} (\texttt{+31.1\% con flag DQ}, motivata dall'aggiunta delle 12 colonne di governance e dalla densificazione LOCF), fino all'abbattimento nel livello \textbf{Gold} di MongoDB a \textbf{15.60 MB} (\textbf{-54.1\%} rispetto a Bronze e \textbf{-65.0\%} rispetto a Silver, con indicazione esplicita dell'overhead di \textbf{+2.56 MB} per gli indici B-Tree). \end{itemize}

\section{Containerizzazione Docker, test automatizzati e manutenzione}
Al fine di garantire l'assoluta riproducibilità dell'ambiente software, l'indipendenza dal sistema operativo ospitante e la rapidità di dispiegamento in contesti ospedalieri, l'intero sistema è stato ingegnerizzato e containerizzato mediante Docker e Docker Compose.

L'intera architettura multi-livello del sistema, illustrata nella Figura~\ref{fig:app_architecture}, connette in modo organico l'interfaccia client, il gateway applicativo e il cluster di archiviazione MongoDB.

    \caption{Architettura multi-livello completa dell'applicazione e containerizzazione Docker.}

L'infrastruttura definita nel file \texttt{docker-compose.yml} orchestra due container interconnessi su una rete virtuale dedicata denominata \texttt{vitaldb\_net}:
il container del database \texttt{vitaldb\_mongo}, basato sull'immagine ufficiale di MongoDB 8.0. Il servizio viene avviato configurando automaticamente un Replica Set a singolo nodo (\texttt{--replSet rs0}), prerequisito architetturale per abilitare le funzionalità avanzate di MongoDB. L'integrità dello storage è garantita da un volume persistente su disco, mentre le collezioni, gli schemi JSON e i metadati iniziali vengono predisposti automaticamente all'avvio mediante gli script montati nella directory di inizializzazione \texttt{/docker-entrypoint-initdb.d/};
il container applicativo \texttt{vitaldb\_api}, costruito a partire da un'immagine leggera basata su Python 3.12-slim. Il container incorpora l'interprete dell'API FastAPI, il server ASGI \texttt{uvicorn} e l'insieme delle librerie matematiche necessarie all'esecuzione dei modelli, tra cui \texttt{pymongo}, \texttt{scikit-learn}, \texttt{pandas}, \texttt{numpy} e la versione per CPU di \texttt{torch}.

Un elemento architetturale di rilievo risiede nell'orchestrazione delle dipendenze basata su \textbf{healthcheck} attivi. Poiché l'API richiede che il database non sia soltanto attivo a livello di processo ma abbia completato con successo l'inizializzazione del Replica Set e il caricamento degli schemi, il servizio \texttt{mongo} esegue un controllo ciclico mediante il client nativo \texttt{mongosh}. Lo script verifica che il nodo appartenga allo stato operativo primario o, in caso contrario, ne forza l'inizializzazione (\texttt{rs.initiate}). Nel file di composizione, il container \texttt{api} dichiara la dipendenza:
$$\texttt{depends\_on: \{ mongo: \{ condition: service\_healthy \} \}}$$
Questo meccanismo impedisce che il backend entri in esecuzione prima che il database sia pienamente operativo, azzerando qualsiasi fallimento di connessione all'avvio dello stack. L'intero sistema può quindi essere generato e avviato con un singolo comando:
$$\texttt{docker compose up --build -d}$$

\begin{techbox}[brandNavy]{Isolamento infrastrutturale e resilienza del deployment}
L'orchestrazione Docker garantisce il disaccoppiamento totale tra il calcolo analitico e la persistenza dei dati: il volume permanente preserva le serie storiche e il catalogo di governance a fronte di riavvii del container, mentre la rete isolata \texttt{vitaldb\_net} e il meccanismo di healthcheck chaining proteggono l'integrità del database durante l'avvio a freddo dello stack.
\end{techbox}

\subsection{Verifica sperimentale automatizzata (Pytest) e strumenti di reset}
Per garantire che le regole di \textbf{data governance}, le trasformazioni matematiche del layer \textbf{Silver} e gli algoritmi di \textbf{anomaly detection} mantengano una correttezza formale verificabile a ogni modifica del codice, il progetto è stato corredato da una suite di \textbf{38 test unitari e d'integrazione} basata sul framework \texttt{pytest} (suddivisa nei moduli \texttt{tests/test\_clean.py}, \texttt{tests/test\_detection.py}, \texttt{tests/test\_queries.py} e \texttt{tests/test\_api.py}):
\begin{itemize}
    \item \textbf{Test di bonifica e telemetria Silver (\texttt{test\_clean.py}):} verificano che l'interpolazione lineare colmi esclusivamente i gap interni $\le 5\text{ s}$ lasciando intatte le code finali prive di campioni successivi, che il rilevamento degli outlier avvenga prima del \textbf{forward-fill} senza propagare artefatti nelle righe successive, che i 5 flag \texttt{*\_imputed} traccino separatamente ogni canale e che per ogni traccia sia sempre soddisfatta l'identità $\texttt{observed} + \texttt{imputed} + \texttt{missing} \equiv \texttt{rows\_cleaned}$;
    \item \textbf{Test clinici, isolamento ML e finestre ricorrenti (\texttt{test\_detection.py}):} certificano il silenziamento dello Shock Index e dell'ipotensione severa quando la pressione ha un'età $\texttt{nibp\_age\_s} > 120\text{ s}$, l'assenza di finestre scorrevoli LSTM a cavallo tra pazienti diversi e l'assenza totale di \textbf{data leakage} nel \texttt{.bfill()} raggruppato per \texttt{case\_id} (\texttt{test\_imputation\_no\_bfill\_leakage\_across\_cases});
    \item \textbf{Test di isolamento del catalogo Gold (\texttt{test\_queries.py}):} verificano mediante mock della collezione \texttt{registry} che la funzione \texttt{list\_loaded\_cases()} interroghi rigorosamente il predicato \texttt{\{"status": "committed"\}}, escludendo i casi in stato \texttt{"loading"}, \texttt{"failed"} o privi di stato;
    \item \textbf{Test non distruttivi dell'API REST (\texttt{test\_api.py}):} validano tutte le rotte HTTP di FastAPI. In particolare, per evitare che il test dell'endpoint \texttt{POST /cases/1/detect} sovrascriva o cancelli le anomalie reali prodotte dall'esecuzione dell'intera coorte nel database MongoDB di produzione, il test adotta una tecnica di \textbf{monkeypatching} (\texttt{monkeypatch.setattr(api\_main, "run\_detection\_pipeline", fake\_run\_detection)}). Ciò consente di collaudare la logica di formattazione, sanitizzazione JSON e gestione degli errori dell'API in una frazione di secondo e in totale isolamento dal database.
\end{itemize}

Infine, a supporto dell'operatività ripetibile dell'intero flusso, è stato realizzato lo script di utilità \texttt{scripts/reset\_pipeline.py}. Invocabile da riga di comando con il parametro \texttt{--layer} (\texttt{gold}, \texttt{silver}, \texttt{bronze} o \texttt{all}), lo strumento permette di azzerare in modo selettivo e controllato le collezioni MongoDB (\texttt{vital\_signals}, \texttt{registry}, \texttt{anomalies\_detected}) e i corrispondenti artefatti e report su disco, garantendo la possibilità di rieseguire da zero l'intera pipeline in condizioni perfettamente deterministiche.

\section{Conclusioni, limiti e sviluppi futuri}
Il lavoro svolto ha dimostrato su scala reale — attraverso l'elaborazione di \textbf{500 interventi chirurgici completi} per oltre \textbf{5.4 milioni di secondi di monitoraggio ad alta frequenza} — la fattibilità e l'efficacia di una piattaforma integrata che coniuga l'ingegneria dei dati temporali con il rilevamento ibrido delle anomalie intraoperatorie.

L'adozione della \textbf{Medallion Architecture} ha consentito di strutturare il flusso di raffinamento del dato clinico in stadi rigorosamente governati e collegati da un identificativo di esecuzione univoco (\texttt{run\_id}): la persistenza immutabile e validata dei dati grezzi (\textbf{Bronze}, 33.95 MB), la bonifica conservativa con arricchimento a 18 colonne di metadati di qualità (\textbf{Silver}, 44.52 MB) e l'archiviazione compressa su MongoDB 8.0 Time Series (\textbf{Gold}, \textbf{15.60 MB} di storage puro più 2.56 MB di indici B-Tree). I benchmark quantitativi hanno certificato una riduzione dello spazio fisico dei dati del \textbf{65.0\% rispetto al layer Silver} (e del \textbf{54.1\% rispetto al Bronze}) e un'accelerazione di \textbf{2.2 volte} nei tempi di risposta delle query analitiche sul singolo paziente (\textbf{12.02 ms} contro \textbf{26.95 ms}).

Al contempo, l'approccio ibrido all'\textbf{anomaly detection} ha confermato il valore clinico di affiancare alle regole deterministiche dominio-specifiche (lo \textbf{Shock Index} e l'ipotensione severa, protette dal vincolo di freschezza pressoria $\texttt{nibp\_age\_s} \le 120\text{ s}$) due algoritmi di \textbf{machine learning} non supervisionato (\textbf{Isolation Forest} e \textbf{LSTM Autoencoder} con viste zero-copy), capaci di conseguire valori di PR-AUC pari a $2.2\times$ e $1.4\times$ la baseline casuale e di intercettare alterazioni multivariate prodromiche non visibili alle soglie statiche.

In un'ottica di rigore scientifico, è fondamentale riassumere i limiti intrinseci dell'architettura e le soluzioni di mitigazione adottate:
\begin{enumerate}
    \item \textbf{Emulazione applicativa delle garanzie Lakehouse:} l'assenza di transazioni multi-documento e di validatori \texttt{\$jsonSchema} nativi sulle \textbf{Time Series Collection} di MongoDB impedisce un'atomicità fisica ACID tra la collezione \texttt{vital\_signals} e il catalogo \texttt{registry}. Questo limite strutturale è stato tuttavia neutralizzato a livello applicativo mediante il protocollo di caricamento a due fasi (\texttt{loading} $\to$ \texttt{committed} con recovery automatico all'avvio), la validazione preventiva dei contratti (\texttt{validate\_records}) e il pattern \textit{Insert-Before-Delete} per le anomalie;
    \item \textbf{Natura della sparsità e della soglia non supervisionata:} la sparsità logica dei sensori dopo il \textbf{forward-fill} rimane pari al \textbf{26.3\%} anche nel layer \textbf{Gold}, pur occupando \textbf{0 byte fisici} grazie all'omissione BSON dei campi nulli. Analogamente, nei modelli non supervisionati la quota del 5\% (\texttt{contamination=0.05} e $95^\circ$ percentile) opera come un selettore dei punteggi più estremi a livello di coorte; la validazione clinica definitiva richiede pertanto il confronto futuro con annotazioni mediche indipendenti;
    \item \textbf{Ancoraggio temporale convenzionale:} l'asse temporale è normalizzato su una data di riferimento (\texttt{2020-01-01 + Time}) per tutelare l'anonimato dei pazienti del dataset pubblico VitalDB; in un dispiegamento ospedaliero reale i campioni utilizzeranno il timestamp assoluto di sala operatoria.
\end{enumerate}

Da un punto di vista normativo e clinico, un sistema di supporto alle decisioni cliniche (\textbf{Clinical Decision Support System}, CDSS) destinato alla sala operatoria deve sottostare a stringenti requisiti di sicurezza. In ambito europeo, il Regolamento sui Dispositivi Medici (MDR 2017/745) classifica i software di monitoraggio diagnostico in classe IIa o IIb, imponendo la validazione prospettica della frequenza dei falsi allarmi per prevenire l'affaticamento da allarme (\textbf{alarm fatigue}) nel personale anestesiologico, unitamente alla piena conformità al GDPR mediante pseudonimizzazione e cifratura a riposo.

Tra le direttrici di sviluppo futuro più promettenti figurano:
\begin{itemize}
    \item \textbf{Estensione granulare della Lineage MLOps a livello di singolo documento:} l'evoluzione del tracciamento di provenienza mediante l'inserimento diretto, all'interno di ciascun documento di \texttt{vital\_signals} e \texttt{anomalies\_detected}, di due identificativi distinti: il \texttt{pipeline\_run\_id} (che identifica la versione dei dati Gold) e il \texttt{detection\_run\_id} (che identifica la specifica esecuzione e configurazione di iperparametri dei modelli ML). Ciò consentirà di storicizzare e confrontare l'evoluzione predittiva di diverse versioni degli algoritmi sulla stessa coorte senza necessità di operazioni di join con il catalogo;
    \item \textbf{Streaming Data Engineering in tempo reale:} l'integrazione di broker di messaggistica distribuiti (quali Apache Kafka o Redpanda) per trasformare l'ingestione da micro-batch a flusso continuo sub-secondo direttamente interfacciato con i monitor di sala operatoria;
    \item \textbf{Ampliamento del pannello multiparametrico ed Explainable AI (XAI):} l'inclusione della pressione arteriosa cruenta invasiva (ART), della capnografia di fine espirazione ($EtCO_2$) e della profondità dell'anestesia (BIS), abbinata a tecniche di spiegabilità basate sui valori di Shapley (\textbf{SHAP}) per indicare istantaneamente al medico quali variabili abbiano innescato l'allarme del modello neurale.
\end{itemize}
