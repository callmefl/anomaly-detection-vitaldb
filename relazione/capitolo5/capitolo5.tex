\section{Backend REST API con FastAPI}
L'integrazione e la fruizione dei dati archiviati nel livello \textbf{Gold} di MongoDB e l'esecuzione degli algoritmi di rilevamento delle anomalie sono orchestrate da un backend sviluppato in linguaggio Python mediante il framework \textbf{FastAPI}.

La scelta di FastAPI è motivata dalle elevate prestazioni del suo motore asincrono basato su \textbf{Starlette} e \textbf{Pydantic}, che consentono la validazione rigorosa dei parametri di richiesta, la serializzazione nativa dei documenti BSON in formato JSON e la generazione automatica della documentazione interattiva OpenAPI (disponibile all'indirizzo \texttt{/docs}). Il servizio REST opera all'interno del container applicativo \texttt{vitaldb\_api} sulla porta di rete 8000 ed è implementato nel file \texttt{api/main.py}.

Dal punto di vista dell'efficienza delle risorse, il backend gestisce la connettività verso MongoDB mediante un'unica istanza globale del client \texttt{pymongo.MongoClient}. Questo accorgimento implementa un pool di connessioni riutilizzabili (\textbf{connection pooling}) che mantiene aperti i socket TCP tra le varie richieste HTTP, azzerando il costo di negoziazione dell'handshake di rete per ciascuna chiamata all'API. Inoltre, prima della trasmissione dei dati sulla rete, il backend esegue una bonifica dei valori numerici: i valori non validi o mancanti (\texttt{np.nan}) vengono convertiti nel valore Python \texttt{None}, serializzato nel corrispondente valore \texttt{null} standard dello standard JSON. Questa sanitizzazione previene la generazione di token non standard \texttt{NaN}, che provocherebbero errori di decodifica bloccanti nei parser JavaScript dei browser moderni (\texttt{JSON.parse}).

L'interfaccia espone un insieme organico di rotte operative:
l'endpoint \texttt{GET /health}, che svolge la funzione di monitoraggio dello stato di salute del container ed effettua un'interrogazione di ping al database. Esso restituisce un oggetto strutturato contenente lo stato della connettività e le statistiche aggregate di sistema: il numero di casi censiti nel \texttt{registry}, il totale dei punti temporali archiviati in \texttt{vital\_signals} e il conteggio cumulativo delle anomalie salvate in \texttt{anomalies\_detected};
l'endpoint \texttt{GET /cases}, che estrae l'elenco dei casi clinici registrati nel catalogo. Per prevenire il classico degrado prestazionale dovuto al problema delle $N+1$ query (in cui per ogni caso verrebbe effettuata una lettura distinta per recuperare reparto, età e sesso del paziente), il metodo adotta un'unica pipeline di aggregazione MongoDB con operatori \texttt{\$group} e \texttt{\$first}. Questa ottimizzazione riduce l'intero recupero anagrafico a due sole operazioni complessive sul database;
l'endpoint \texttt{GET /cases/\{case\_id\}/series}, che restituisce la serie temporale biometrica del paziente richiesto. L'endpoint supporta il parametro opzionale \texttt{window\_seconds} (con valori selezionabili quali 30, 60 o 300 secondi): quando specificato, l'API attiva la pipeline di aggregazione temporale descritta nel capitolo precedente con operatore \texttt{\$dateTrunc}, riducendo drasticamente il payload di rete trasferito al browser per tracciati che si estendono per molte ore;
l'endpoint \texttt{POST /cases/\{case\_id\}/detect}, la cui implementazione è descritta nel Listato~\ref{lst:api_detect}, innesca l'esecuzione on-demand dell'intera pipeline di \textbf{anomaly detection} sul paziente selezionato. L'elaborazione calcola contestualmente le regole cliniche dello \textbf{Shock Index} e dell'ipotensione severa, unitamente alle inferenze dei modelli \textbf{Isolation Forest} e \textbf{Autoencoder}. I riscontri anomali vengono persistiti nella collezione \texttt{anomalies\_detected} e restituiti al client suddivisi per metodologia;
gli endpoint dedicati alla trasparenza e alla governance, segnatamente \texttt{GET /quality}, \texttt{GET /benchmark} e \texttt{GET /evaluation}, che espongono direttamente in formato JSON i report di bonifica del livello \textbf{Silver}, i risultati del benchmark di storage e latenza, e le metriche quantitative di validazione dei modelli di \textbf{machine learning}.

\begin{lstlisting}[caption={Definizione della rotta REST per l'esecuzione della pipeline di anomaly detection in FastAPI.}, label={lst:api_detect}]
// Endpoint implementato nel backend FastAPI (api/main.py)
@app.post("/cases/{case_id}/detect")
def detect_case(case_id: int):
    """Esegue la pipeline di anomaly detection multilivello sul caso specificato."""
    db = get_db()
    df = get_case_series(db, case_id)
    if df.empty:
        raise HTTPException(status_code=404, detail=f"Nessun dato per il caso #{case_id}")

    # Esegue regole cliniche (Shock Index, Ipotensione Severa) ed algoritmi ML
    anomalies_df = run_detection_pipeline(df, case_id)

    # Persistenza atomica dei riscontri nella collezione MongoDB 'anomalies_detected'
    db['anomalies_detected'].delete_many({"case_id": case_id})
    if not anomalies_df.empty:
        records = anomalies_df.to_dict(orient="records")
        db['anomalies_detected'].insert_many(records)

    return {
        "status": "ok",
        "case_id": case_id,
        "total_anomalies": len(anomalies_df),
        "methods_summary": {
            "shock_index": int(anomalies_df['shock_index_anomaly'].sum()),
            "severe_hypotension": int(anomalies_df['severe_hypotension_anomaly'].sum()),
            "isolation_forest": int(anomalies_df['isolation_forest_anomaly'].sum()),
            "autoencoder": int(anomalies_df['autoencoder_anomaly'].sum())
        }
    }
\end{lstlisting}

Accanto agli endpoint analitici, FastAPI ospita due montaggi di file statici: la rotta \texttt{/dashboard}, che distribuisce l'intera interfaccia web interattiva, e la rotta \texttt{/presentazione}, che rende fruibili le slide illustrative del progetto per la discussione accademica.

\section{Dashboard web e interfaccia utente interattiva}
A corredo dell'infrastruttura dati è stata sviluppata un'interfaccia grafica web concepita per consentire al personale sanitario e all'analista di esplorare i tracciati biometrici, analizzare le anomalie e ispezionare i parametri di governance. L'applicazione rifugge la complessità e la pesantezza di framework monolitici, impiegando standard aperti del web: un'architettura in HTML5 semantico, fogli di stile CSS3 con variabili a token per la gestione dinamica del tema chiaro e scuro (\textbf{light/dark mode}), e logica di coordinamento in JavaScript puro.

Per garantire modularità e manutenibilità senza richiedere strumenti di compilazione esterni quali Webpack o Vite, il codice adotta un sistema di caricamento asincrono a componenti parziali implementato nello script \texttt{dashboard/js/loader.js}. Il file principale \texttt{index.html} definisce dei contenitori dichiarativi denominati slot mediante l'attributo personalizzato \texttt{data-include} (ad esempio \texttt{<div data-include="partials/sidebar.html"></div>}). All'avvio dell'applicazione, la funzione \texttt{loadPartials} individua tutti gli slot mediante \texttt{querySelectorAll}, invia richieste HTTP parallele tramite \texttt{Promise.all} e l'API \texttt{fetch}, e provvede a sostituire ciascun tag con il frammento HTML recuperato. Al fine di impedire che il browser mantenga in cache versioni obsolete dei file durante gli aggiornamenti, il caricatore accoda a ciascuna richiesta un parametro di versione esplicito (\texttt{?v=3.8}), realizzando una tecnica efficace di invalidazione della cache (\textbf{cache busting}).

La piattaforma si articola su due ambienti di lavoro principali, accessibili tramite il commutatore in testata: la vista di telemetria clinica e la vista di governance del \textbf{lakehouse} e benchmark.

        \item il pulsante di attivazione \textbf{Rileva Anomalie}, che inoltra una richiesta asincrona \texttt{POST /detect/\{case\_id\}} al server FastAPI per eseguire in tempo reale l'inferenza congiunta delle regole cliniche e dei modelli di machine learning, persistendo atomicamente i risultati su MongoDB e aggiornando reattivamente l'HUD, i tracciati e il registro clinico.
    \end{itemize}
    \item \textbf{Griglia degli indicatori vitali (Vitals Bento-Grid):} composta da cinque schede metriche interattive che sintetizzano lo stato fisiologico istantaneo e complessivo della registrazione:
    \begin{enumerate}
        \item \textit{Frequenza Cardiaca:} valore corrente medio pari a 81 bpm, corredato dall'intervallo di escursione registrato (minimo 59 bpm, massimo 116 bpm);
        \item \textit{Saturazione $SpO_2$:} valore istantaneo pari al 99.8\%, con indicazione del punto di minimo (\textit{nadir} all'85\%) rispetto alla soglia fisiologica target ($>95\%$);
        \item \textit{Pressione Arteriosa (SBP/DBP):} valori pressori istantanei di sistolica e diastolica (104/67 mmHg), integrati dal calcolo della pressione arteriosa media (MAP media pari a 78 mmHg);
        \item \textit{Shock Index ($HR / SBP$):} valore istantaneo pari a 0.78, contrassegnato con etichetta \textit{Borderline} (intervallo $0.7 - 0.9$) a supporto della diagnosi precoce di ipovolemia;
        \item \textit{Anomalie Totali Uniche:} contatore cumulativo che quantifica il totale degli istanti temporali critici individuati per il caso clinico selezionato (1.939 eventi distinti nel Caso \#2).
    \end{enumerate}
    \item \textbf{Matrice di Rilevamento per Algoritmo (Consensus Matrix):} pannello interattivo a quattro quadranti che scorpora analiticamente il concorso dei quattro algoritmi implementati nel sistema:
    \begin{enumerate}
        \item \textit{Shock Index Clinico} ($HR / SBP > 0.9$): 1.429 istanti di allarme;
        \item \textit{Ipotensione Severa} ($MBP < 65\text{ mmHg} \land SpO_2 < 90\%$): 0 istanti critici;
        \item \textit{Isolation Forest} (rilevamento multivariato non supervisionato): 380 campioni classificati come outlier;
        \item \textit{Autoencoder Neurale LSTM} (scostamento da ricostruzione $MSE > \tau$): 379 campioni anomali.
    \end{enumerate}
    Ciascuna scheda della matrice supporta la funzione di filtro interattivo (\texttt{toggleAlgoHighlight}): facendo clic su una tessera, i grafici sottostanti isolano ed evidenziano cromaticamente soltanto le anomalie riscontrate da quello specifico metodo. Inoltre, un'icona informativa apre una finestra di dialogo modale che descrive la logica algoritmica, la formula matematica e la motivazione clinica della soglia adottata.
\end{itemize}

\subsection{Tracciati telemetrici sincronizzati ed evidenziazione delle anomalie}
L'esplorazione dinamica dei segnali biometrici è affidata a due grafici temporali continui realizzati mediante la libreria grafica \textbf{Chart.js}, presentati nella Figura~\ref{fig:dashboard_telemetry_charts}. Le due viste condividono il medesimo asse temporale UTC e implementano un plugin personalizzato per il mirino verticale sincronizzato (\texttt{synchronizedCrosshairPlugin}): spostando il puntatore del mouse su un qualsiasi istante temporale di una traccia, una linea tratteggiata verticale interseca simultaneamente entrambi i grafici, consentendo al medico di correlare istantaneamente una variazione del ritmo cardiaco con una caduta di pressione o di saturazione d'ossigeno.

\begin{itemize}
    \item \textbf{Traccia I (Frequenza Cardiaca e Saturazione):} impiega un doppio asse delle ordinate (a sinistra la frequenza in scala $40-160$ bpm, a destra la saturazione in scala $80-100\%$). La curva cardiaca (in rosso con interpolazione cubica) e la saturazione (in ciano) sono accompagnate da una fascia orizzontale di riferimento clinico che delimita la normocardia ($60-100$ bpm) e segnala il limite inferiore di ipossia moderata ($<95\%$). Come illustrato nella Figura~\ref{fig:dashboard_telemetry_hr_spo2}, al passaggio del cursore un tooltip fluttuante espone il valore esatto registrato (ad esempio, ore 00:14:00 con $HR = 61.93$ bpm e $SpO_2 = 100\%$). Quando viene eseguita la procedura di rilevamento, gli istanti temporali anomali vengono disegnati direttamente sopra le curve del segnale sotto forma di evidenti marcatori circolari arancioni.
    \item \textbf{Traccia II (Pressione Arteriosa NIBP):} visualizza simultaneamente la pressione sistolica (curva continua giallo/arancione), diastolica (curva verde) e media arteriosa (curva viola tratteggiata). Il grafico evidenzia la linea critica di ipotensione a $MBP = 65$ mmHg, soglia clinica sotto la quale sussiste un concreto pericolo di ipoperfusione degli organi vitali. I punti anomali contrassegnati evidenziano tempestivamente sia cadute ipotensive repentine sia bruschi picchi ipertensivi intraoperatori.
\end{itemize}

Al di sotto dei tracciati grafici è collocato il \textbf{Registro Clinico degli Eventi Anomali} (Figura~\ref{fig:dashboard_anomalies_table}), un modulo tabellare progettato per l'ispezione analitica e la validazione post-operatoria delle segnalazioni. 

Il registro visualizza tutti i 1.939 eventi individuati per il caso clinico selezionato e integra:
\begin{itemize}
    \item menu a tendina per il filtraggio rapido in base alla severità dell'allarme o alla tipologia di evento;
    \item il pulsante \textbf{Esporta CSV}, che genera istantaneamente il download dell'intero registro anomalo per facilitare l'archiviazione nella cartella clinica elettronica (EHR) o per condurre analisi statistiche retrospettive offline;
    \item una struttura tabellare analitica a otto colonne:
    \begin{enumerate}
        \item \textbf{\#}: indice progressivo della segnalazione;
        \item \textbf{TIMESTAMP (UTC)}: marcatura temporale esatta al secondo dell'evento rilevato (ad esempio, \texttt{2020-01-01 00:00:04});
        \item \textbf{LIVELLO SEVERITÀ}: classificazione a badge cromatico graduato che sintetizza il consenso algoritmico: \textit{Advisory} (quando un solo metodo rileva l'anomalia), \textit{Warning} (quando concorrono due metodi) o \textit{Critical} (quando tre o quattro algoritmi concordano sulla criticità dell'istante);
        \item \textbf{HR (BPM)}: frequenza cardiaca istantanea registrata;
        \item \textbf{$SPO_2$ (\%)}: saturazione periferica d'ossigeno rilevata all'istante dell'allarme (evidenziando cali precoci, ad esempio il 90\% alla riga 1);
        \item \textbf{NIBP (SBP/DBP)}: pressione sistolica e diastolica concomitante (ad esempio, 128/75 mmHg alla riga 11);
        \item \textbf{SHOCK INDEX}: valore numerico istantaneo del rapporto $HR / SBP$;
        \item \textbf{ALGORITMI RILEVATORI}: tag compatti che indicano puntualmente quale modello ha sollevato l'allarme (\texttt{IsoForest}, \texttt{Autoencoder}, \texttt{Shock Index}).
    \end{enumerate}
\end{itemize}

\section{Containerizzazione ed orchestrazione con Docker}
Al fine di garantire l'assoluta riproducibilità dell'ambiente software, l'indipendenza dal sistema operativo ospitante e la rapidità di dispiegamento in contesti ospedalieri, l'intero sistema è stato ingegnerizzato e containerizzato mediante Docker e Docker Compose.

L'intera architettura multi-livello del sistema, illustrata nella Figura~\ref{fig:app_architecture}, connette in modo organico l'interfaccia client, il gateway applicativo e il cluster di archiviazione MongoDB.

\begin{figure}[ht]
    \centering
    \resizebox{0.95\textwidth}{!}{\input{app_architecture_tikz.tex}}
    \caption{Architettura multi-livello completa dell'applicazione e containerizzazione Docker.}
    \label{fig:app_architecture}
\end{figure}

L'infrastruttura definita nel file \texttt{docker-compose.yml} orchestra due container interconnessi su una rete virtuale dedicata denominata \texttt{vitaldb\_net}:
il container del database \texttt{vitaldb\_mongo}, basato sull'immagine ufficiale di MongoDB 8.0. Il servizio viene avviato configurando automaticamente un Replica Set a singolo nodo (\texttt{--replSet rs0}), prerequisito architetturale per abilitare le funzionalità transazionali native di MongoDB. L'integrità dello storage è garantita da un volume persistente su disco, mentre le collezioni, gli schemi JSON e i metadati iniziali vengono predisposti automaticamente all'avvio mediante gli script montati nella directory di inizializzazione \texttt{/docker-entrypoint-initdb.d/};
il container applicativo \texttt{vitaldb\_api}, costruito a partire da un'immagine leggera basata su Python 3.12-slim. Il container incorpora l'interprete dell'API FastAPI, il server ASGI \texttt{uvicorn} e l'insieme delle librerie matematiche necessarie all'esecuzione dei modelli, tra cui \texttt{pymongo}, \texttt{scikit-learn}, \texttt{pandas}, \texttt{numpy} e la versione per CPU di \texttt{torch}.

Un elemento architetturale di rilievo risiede nell'orchestrazione delle dipendenze basata su \textbf{healthcheck} attivi. Poiché l'API richiede che il database non sia soltanto attivo a livello di processo ma abbia completato con successo l'inizializzazione del Replica Set e il caricamento degli schemi, il servizio \texttt{mongo} esegue un controllo ciclico mediante il client nativo \texttt{mongosh}. Lo script verifica che il nodo appartenga allo stato operativo primario o, in caso contrario, ne forza l'inizializzazione (\texttt{rs.initiate}). Nel file di composizione, il container \texttt{api} dichiara la dipendenza:
$$\texttt{depends\_on: \{ mongo: \{ condition: service\_healthy \} \}}$$
Questo meccanismo impedisce che il backend entri in esecuzione prima che il database sia pienamente operativo, azzerando qualsiasi fallimento di connessione all'avvio dello stack. L'intero sistema può quindi essere generato e avviato con un singolo comando:
$$\texttt{docker compose up --build -d}$$

\begin{techbox}[brandNavy]{Isolamento infrastrutturale e resilienza del deployment}
L'orchestrazione Docker garantisce il disaccoppiamento totale tra il calcolo analitico e la persistenza dei dati: il volume permanente preserva le serie storiche e il catalogo di governance a fronte di riavvii del container, mentre la rete isolata \texttt{vitaldb\_net} e il meccanismo di healthcheck chaining proteggono l'integrità delle transazioni durante l'avvio a freddo dello stack.
\end{techbox}

\section{Conclusioni, limiti e sviluppi futuri}
Il lavoro svolto ha dimostrato con successo la fattibilità e l'efficacia di una piattaforma integrata che combina l'ingegneria dei dati temporali con l'analisi automatizzata delle anomalie per il monitoraggio chirurgico intraoperatorio.

L'adozione della \textbf{Medallion Architecture} ha consentito di strutturare il flusso di raffinamento del dato clinico in stadi chiari e governati, isolando la persistenza dei dati grezzi (\textbf{Bronze}), la bonifica e il partizionamento (\textbf{Silver}) e l'archiviazione ottimizzata su MongoDB Time Series (\textbf{Gold}). I benchmark quantitativi hanno evidenziato vantaggi misurabili: una contrazione dello spazio su disco dell'89.1\% e un'accelerazione di 3.7 volte nei tempi di risposta delle query temporali.

Al contempo, l'approccio ibrido all'\textbf{anomaly detection} ha confermato l'importanza di affiancare le regole cliniche deterministiche (lo \textbf{Shock Index} e l'ipotensione severa) ad algoritmi di \textbf{machine learning} non supervisionato (\textbf{Isolation Forest} e \textbf{LSTM Autoencoder}), garantendo una copertura multilivello delle alterazioni emodinamiche.

In un'ottica di onestà scientifica, è fondamentale riassumere i limiti attuali dell'architettura:
la soluzione di \textbf{data governance} costituisce un'emulazione artigianale dei principi del \textbf{data lakehouse}. L'impossibilità di eseguire inserimenti nelle \textbf{Time Series Collection} di MongoDB all'interno di transazioni multi-documento impedisce il conseguimento di un'atomicità fisica nativa tra i dati temporali e il catalogo \texttt{registry}, obbligando a ricorrere a strategie applicative di compensazione;
l'azzeramento dei valori nulli nel livello \textbf{Gold} deriva dalla rimozione delle righe vuote e dall'omissione dei campi privi di valore nei documenti BSON; la perdita di continuità temporale correlata alla cancellazione di campioni nel \textbf{Silver} impone cautela analitica;
l'asse temporale è attualmente ancorato a una data convenzionale fissa (\texttt{2020-01-01}), che in un contesto produttivo reale dovrà essere sostituita dalla marcatura temporale esatta dell'anestesia.

Da un punto di vista normativo e clinico, un sistema di supporto alle decisioni cliniche (\textbf{Clinical Decision Support System}, CDSS) destinato alla sala operatoria deve sottostare a stringenti requisiti di sicurezza. In ambito europeo, il Regolamento sui Dispositivi Medici (MDR 2017/745) classifica i software diagnostici in classe IIa o superiore, imponendo la validazione clinica della frequenza dei falsi allarmi per prevenire la cosiddetta fatica da allarme (\textbf{alarm fatigue}) nel personale sanitario. Inoltre, la gestione dei dati biometrici ad alta fedeltà richiede la rigorosa conformità al GDPR attraverso tecniche di pseudonimizzazione forte e cifratura dello storage a riposo.

Tra le direttrici di sviluppo futuro più promettenti figurano:
l'evoluzione verso un'architettura di \textbf{streaming data engineering} mediante l'integrazione di broker di messaggistica distribuiti (quali Apache Kafka o Redpanda), per consentire l'ingestione e la segnalazione delle anomalie in tempo reale con latenze inferiori al secondo direttamente durante l'intervento chirurgico;
l'estensione del perimetro analitico a ulteriori parametri biologici, quali la temperatura corporea centrale, la concentrazione di anidride carbonica a fine espirazione (capnografia $EtCO_2$) e le frazioni di gas anestetici alogenati;
l'introduzione di moduli di spiegabilità per l'intelligenza artificiale (\textbf{Explainable AI}), sfruttando ad esempio i valori di Shapley (SHAP) per fornire all'anestesista una motivazione quantitativa trasparente su quali parametri abbiano maggiormente contribuito a generare l'allarme multivariato.
