\section{Servizi REST con FastAPI}
Per mettere in comunicazione il livello gold di MongoDB, il motore ibrido di rilevamento delle anomalie e l'interfaccia utente, \`e stato realizzato un servizio web REST in Python basato su FastAPI, definito nel modulo \texttt{api/main.py} ed eseguito all'interno del container Docker \texttt{vitaldb\_api} sulla porta \texttt{8000}. L'adozione di FastAPI ha permesso di dichiarare le rotte HTTP con validazione automatica dei tipi per i parametri di percorso e di query (come \texttt{case\_id: int} e \texttt{window\_seconds: Optional[int]}), di esporre la documentazione interattiva OpenAPI all'indirizzo \texttt{http://localhost:8000/docs} e di montare tramite \texttt{StaticFiles} nello stesso processo \texttt{uvicorn} anche le cartelle statiche \texttt{/dashboard} e \texttt{/presentazione}, evitando l'aggiunta di un terzo container dedicato a un server web esterno.

Sul piano della gestione delle connessioni, il modulo mantiene un riferimento globale \texttt{\_client: Optional[MongoClient] = None} inizializzato al primo utilizzo dalla funzione \texttt{get\_db()}, consentendo a tutte le richieste HTTP concorrenti di condividere il medesimo pool di connessioni TCP di PyMongo verso il container \texttt{vitaldb\_mongo}. Inoltre, prima di serializzare le risposte per il client, il backend converte sistematicamente eventuali valori \texttt{np.nan} residui di Pandas in oggetti \texttt{None} (tradotti nello standard JSON come \texttt{null}), garantendo la piena compatibilit\`a con il parser nativo dei browser web.

L'interfaccia REST si articola su sette endpoint principali: la rotta diagnostica \texttt{GET /health} verifica il collegamento con MongoDB tramite comando \texttt{ping} e restituisce i conteggi dei documenti presenti in \texttt{registry}, \texttt{vital\_signals} e \texttt{anomalies\_detected}; la rotta \texttt{GET /cases} restituisce la lista dei $500$ pazienti certificati con i relativi metadati anagrafici e di reparto; l'endpoint \texttt{GET /cases/\{case\_id\}/series} fornisce la serie storica del singolo intervento a piena risoluzione ($1\text{ Hz}$) tramite \texttt{get\_case\_series} oppure ridotta su finestre temporali tramite \texttt{downsample\_case} quando viene specificato il parametro \texttt{window\_seconds}; le tre rotte \texttt{GET /quality}, \texttt{GET /benchmark} e \texttt{GET /evaluation} espongono infine i file JSON generati dagli script di analisi. A queste rotte di lettura si affianca l'endpoint \texttt{POST /cases/\{case\_id\}/detect}, mostrato nel Listato~\ref{lst:api_detect}, che avvia su richiesta l'analisi ibrida sul paziente selezionato invocando \texttt{run\_detection\_pipeline(db, [case\_id])} e restituisce il riepilogo per metodo (\texttt{summary\_by\_method}) insieme al dettaglio cronologico dei secondi anomali.

@app.post("/cases/{case_id}/detect")
def detect_case(case_id: int):
    """Esegue l'algoritmo multilivello di anomaly detection sul caso specificato."""
    db = get_db()
    df = run_detection_pipeline(db, [case_id])
    if df.empty:
        raise HTTPException(status_code=404, detail=f"Nessun dato per case_id={case_id}")

    flag_cols = [c for c in df.columns if c.endswith("_anomaly")]
    anomalous_rows = df[df[flag_cols].any(axis=1)]
    summary_by_method = {col.replace("_anomaly", ""): int(df[col].sum()) for col in flag_cols}

    def _val(row, col):
        return float(row[col]) if col in row and pd.notna(row[col]) else None

    anomalies = []
    for _, row in anomalous_rows.iterrows():
        methods = [c.replace("_anomaly", "") for c in flag_cols if bool(row[c])]
        si_val = _val(row, "shock_index")
        anomalies.append({
            "timestamp": str(row["timestamp"]),
            "methods": methods,
            "hr": _val(row, "Solar8000_HR"), "spo2": _val(row, "Solar8000_PLETH_SPO2"),
            "sbp": _val(row, "Solar8000_NIBP_SBP"), "dbp": _val(row, "Solar8000_NIBP_DBP"),
            "mbp": _val(row, "Solar8000_NIBP_MBP"),
            "shock_index": round(si_val, 3) if si_val is not None else None
        })

    return {
        "case_id": case_id,
        "anomaly_count": len(anomalies),
        "summary_by_method": summary_by_method,
        "anomalies": anomalies,
    }
\end{lstlisting}

\section{Dashboard web per l'esplorazione clinica e architetturale}
L'interfaccia grafica del sistema, accessibile all'indirizzo \texttt{http://localhost:8000/dashboard}, \`e stata sviluppata utilizzando HTML5, CSS3 e JavaScript standard abbinati alla libreria Chart.js per la rappresentazione delle serie storiche, senza introdurre framework complessi come React o Angular che avrebbero richiesto una catena di compilazione Node.js dedicata dentro il container Docker. Per mantenere comunque il codice sorgente ordinato e diviso per responsabilit\`a, lo script \texttt{dashboard/js/loader.js} carica dinamicamente all'avvio i frammenti HTML dichiarati tramite l'attributo \texttt{data-include} dentro \texttt{dashboard/index.html} (come la barra laterale, l'intestazione e le singole viste) utilizzando chiamate \texttt{fetch} parallele con parametro di versione \texttt{?v=3.9} per aggirare la cache del browser.

\section{Containerizzazione Docker, orchestrazione e test automatici}
Per assicurare che l'intero ambiente sia riproducibile su qualsiasi sistema operativo senza richiedere l'installazione manuale di MongoDB 8.0 o di librerie scientifiche locali, la piattaforma \`e stata incapsulata in due container gestiti da \texttt{docker-compose.yml}.

Sulla rete virtuale isolata \texttt{vitaldb\_net} operano il container \texttt{vitaldb\_mongo}, basato sull'immagine ufficiale \texttt{mongo:8.0} avviata con l'opzione \texttt{--replSet rs0} e dotata di una sonda di controllo (\texttt{healthcheck}) che verifica o inizializza automaticamente il replica set tramite \texttt{mongosh}, e il container \texttt{vitaldb\_api}, costruito a partire da \texttt{python:3.12-slim} con tutte le dipendenze di \texttt{requirements.txt} (inclusa la distribuzione CPU di PyTorch). Grazie alla direttiva \texttt{depends\_on} vincolata alla condizione \texttt{service\_healthy}, il servizio FastAPI attende che il motore MongoDB abbia completato l'elezione del nodo primario prima di accettare richieste sulla porta \texttt{8000}.

L'esecuzione ordinata dei sei stadi della pipeline sui $500$ casi clinici — scaricamento bronze (\texttt{download.py}), pulizia silver (\texttt{clean.py}), caricamento gold (\texttt{load\_mongo.py}), rilevamento delle anomalie (\texttt{detector.py}), benchmark delle prestazioni (\texttt{benchmark\_etl.py}) e valutazione dei modelli (\texttt{evaluate\_models.py}) — \`e governata dallo script orchestratore \texttt{scripts/run\_pipeline.py}, avviabile con un unico comando:
$$\texttt{docker exec vitaldb\_api python -u scripts/run\_pipeline.py}$$
L'orchestratore lancia i sei moduli in sequenza controllando il codice di uscita di ciascun sottoprocesso e interrompe immediatamente la catena qualora una fase restituisca un errore (\texttt{exit code != 0}), evitando disallineamenti tra i file su disco e le collezioni del database. A supporto dei cicli di sviluppo \`e stato inoltre realizzato lo script \texttt{scripts/reset\_pipeline.py}, che previa conferma (\texttt{--yes}) svuota le collezioni MongoDB e rimuove i file Parquet e i report JSON per consentire una ripartenza da zero.

La correttezza funzionale dell'intero codice \`e presidiata da una suite di 38 test automatici eseguibili tramite \texttt{pytest} e distribuiti in sei moduli nella cartella \texttt{tests/}, riepilogati nella Tabella~\ref{tab:pytest_suite}. In particolare, nei test dell'endpoint \texttt{POST /cases/\{id\}/detect} dentro \texttt{tests/test\_api.py} viene sostituito dinamicamente il metodo di scrittura \texttt{save\_anomalies\_to\_mongo} tramite \texttt{monkeypatch}, cos\`i da verificare l'intera catena di calcolo senza sovrascrivere nel database le anomalie reali calcolate sulla coorte di $500$ pazienti.

\section{Conclusioni, analisi dei limiti e sviluppi futuri}
Il lavoro svolto ha permesso di progettare, implementare e validare su una coorte reale di 500 interventi chirurgici estratti da VitalDB (5.565.384 secondi grezzi nel livello bronze e 5.402.386 secondi bonificati nei livelli silver e gold) una piattaforma completa di ingegneria dei dati e rilevamento automatico delle anomalie. I risultati sperimentali confermano anzitutto il valore pratico della separazione dei ruoli nell'architettura medallion: conservare i tracciati originali in Apache Parquet nel livello bronze (33,95 MB) ha svincolato lo sviluppo dai tempi di rete dell'API remota; utilizzare il livello silver (44,52 MB, $+31,1\%$) per arricchire le tabelle con dodici colonne di qualit\`a e ridurre i valori mancanti dal $66,3\%$ al $26,3\%$ senza cancellare gli outlier ha garantito una tracciabilit\`a trasparente; infine, modellare il livello gold sulle collezioni temporali di MongoDB 8.0 ha compresso i dati fisici a 15,60 MB ($-65,0\%$ rispetto a silver, oltre a 2,56 MB di indici B-Tree) dimezzando i tempi di risposta sulle interrogazioni per singolo paziente (12,02 ms contro 26,95 ms, pari a un fattore 2,2$\times$). Alrettanto determinante si \`e rivelata la cura nella preparazione del dato per gli algoritmi a valle: rilevare gli outlier prima della propagazione in avanti, distinguere l'orizzonte di mantenimento pressorio nel livello silver ($300\text{ s}$) dal vincolo di freschezza per le regole cliniche ($120\text{ s}$) e confinare il \texttt{.bfill()} dentro ciascun \texttt{case\_id} hanno evitato distorsioni sistematiche nei modelli.

Accanto ai risultati raggiunti, un'analisi critica dell'architettura realizzata consente di mettere in luce con trasparenza i limiti progettuali e operativi del sistema. Il limite strutturale primario risiede nella natura esclusivamente batch e retrospettiva dell'intera pipeline: l'infrastruttura presuppone che l'intervento chirurgico sia gi\`a interamente concluso e archiviato su file prima di avviare le fasi di bonifica, caricamento e rilevamento. In un contesto clinico reale di sala operatoria o di terapia intensiva, tuttavia, i parametri vitali vengono generati come flussi continui secondo per secondo ($1\text{ Hz}$): l'attuale implementazione non dispone di un layer di ingestione in streaming (ad esempio tramite broker come Apache Kafka o protocolli IoT come MQTT) n\'e di un motore di elaborazione su code temporali scorrevoli dal vivo (come Apache Flink), precludendo l'emissione di allarmi istantanei al secondo esatto in cui l'evento avverso si manifesta al monitor del paziente.

Per quanto riguarda i livelli bronze e silver, il controllo sui file gi\`a presenti su disco prima di applicare lo stato \texttt{skipped\_existing} verifica la presenza delle colonne e il passo di campionamento tra i primi due secondi senza ricalcolare un'impronta crittografica dell'intero file Parquet, mentre i referti salvati in \texttt{lab\_data.parquet} vengono storicizzati ma non sono ancora integrati con le serie a $1\text{ Hz}$. Nel livello silver, inoltre, la scelta di non rimuovere fisicamente i campioni marcati come \texttt{*\_outlier} fa s\`i che la loro esclusione effettiva avvenga solo al momento della lettura in \texttt{load\_from\_gold}, e non \`e ancora previsto un filtro bloccante a livello di intero paziente (quality gate) che escluda dal caricamento nel livello gold gli interventi caratterizzati da una copertura sensoriale molto bassa.

Sul fronte del livello gold e del data lakehouse applicativo, le restrizioni native delle collezioni temporali di MongoDB 8.0 — che non supportano transazioni multi-documento verso il \texttt{registry} n\'e validatori \texttt{\$jsonSchema} su \texttt{vital\_signals} — implicano che l'atomicit\`a del caricamento a due fasi e il controllo dei tipi sulle misure dipendano dal passaggio attraverso gli script Python e dalla procedura di recupero \texttt{recover\_incomplete\_loads}, anzich\'e essere imposti dal motore del database su qualsiasi scrittura esterna. Allo stesso modo, l'identificativo di esecuzione \texttt{run\_id} \`e registrato nel catalogo \texttt{registry} e nei quattro file JSON senza essere replicato dentro ciascuno dei $5,4$ milioni di documenti temporali, l'asse del tempo parte dalla data convenzionale del $1^\circ$ gennaio $2020$ poich\'e VitalDB fornisce solo secondi relativi anonimizzati, e l'interrogazione \texttt{GET /cases} richiede ancora uno stadio di raggruppamento \texttt{\$group} su \texttt{vital\_signals} per recuperare reparto, et\`a e sesso dei pazienti. Anche i risultati del benchmark di latenza vanno letti nel loro contesto specifico: il vantaggio di $2,2\times$ misura l'interrogazione selettiva di un singolo paziente con dati caldi in memoria su macchina singola, mentre su scansioni analitiche dell'intera coorte senza filtri la lettura colonnare diretta dei file Parquet rimane altamente competitiva.

Relativamente al modulo di anomaly detection e ai servizi applicativi, l'impostazione di \texttt{contamination=0.05} in isolation forest e del $95^\circ$ percentile nell'autoencoder LSTM fissa per costruzione al $5\%$ la frazione di campioni segnalati, configurando i due algoritmi come meccanismi di ordinamento per severit\`a anzich\'e come stimatori autonomi della prevalenza patologica, mentre la valutazione tramite PR-AUC ($0,105$ e $0,067$) misura la concordanza interna rispetto alle regole cliniche in assenza di diagnosi mediche indipendenti. Inoltre, il sistema attuale non salva su disco i pesi dei modelli addestrati sull'intera coorte (\texttt{.pkl} e \texttt{.pt}) e non espone una rotta \texttt{GET /cases/\{id\}/anomalies} di sola lettura: quando l'utente avvia il rilevamento dalla dashboard tramite \texttt{POST /cases/\{id\}/detect}, la pipeline riaddestra i modelli sul solo paziente selezionato e aggiorna per quel caso i record in \texttt{anomalies\_detected}. Infine, sul piano dell'interfaccia web, la vista architetturale limita la tabella di dettaglio ai primi $15$ pazienti per mantenere reattivo il browser e non espone ancora nell'intestazione grafica gli identificativi \texttt{run\_id} e \texttt{pipeline\_version}.

Questi stessi limiti tracciano in modo diretto le principali direttrici di sviluppo futuro del progetto: la serializzazione su disco dello \texttt{StandardScaler}, del modello \texttt{IsolationForest} e dei pesi PyTorch dell'autoencoder addestrati sui $500$ casi, separando nell'API la consultazione immediata degli allarmi precalcolati (\texttt{GET /cases/\{id\}/anomalies}) dal ricalcolo esplicito; l'inserimento nel documento del catalogo \texttt{registry} dei campi anagrafici (\texttt{department}, \texttt{age}, \texttt{sex}) per servire la rotta \texttt{GET /cases} senza interrogare \texttt{vital\_signals}, affiancato da un identificativo \texttt{detection\_run\_id} nei record di anomalia; l'introduzione nel livello silver di una soglia minima di copertura per paziente prima della promozione a gold; e infine l'evoluzione verso un'architettura ibrida (\textit{streaming} e \textit{batch}) mediante code a eventi (come Apache Kafka o MQTT) per consentire il monitoraggio dal vivo durante l'intervento chirurgico, affiancata dal passaggio dello script \texttt{run\_pipeline.py} a un orchestratore come Apache Airflow o Prefect ed estendendo l'analisi anche alla pressione arteriosa invasiva (\texttt{ART}), alla capnografia ($\text{EtCO}_2$) e all'indice bispettrale (\texttt{BIS}).\enlargethispage{\baselineskip}
